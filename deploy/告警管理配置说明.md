# AIOps 告警管理 · 配置说明

> 面向医院内网环境：**不需要改代码**，全部在界面上配置。
> 入口：左侧菜单 **告警配置**（告警中心页面右上角也有入口按钮）。

---

## 一、整体思路

```
指标采集: Agent / SNMP / 动环设备(Modbus TCP 主动轮询)
        │
        ▼
   告警规则(阈值)  ──►  判定等级: 提示(warning) / 严重告警(critical)
        │
        ▼
   去抖 + 静默 + 自动恢复
        │
        ▼
   通知渠道: 钉钉 / 企业微信 / 院内短信平台 / 电话告警盒子 / 自定义Webhook
```

**默认策略（开箱即用）**

| 监控对象 | 指标 | 提示阈值 | 告警阈值 |
|---|---|---|---|
| 服务器 | CPU 使用率 | 80% | 90% |
| 服务器 | 内存使用率 | 80% | 90% |
| 服务器 | 磁盘使用率 | 85% | 95% |
| 网络设备 | CPU / 内存 | 80% / 85% | 90% / 95% |
| 存储设备 | 容量使用率 | 80% | 90% |
| 机房温湿度 | 温度 / 湿度 | 30°C / 75% | 35°C / 85% |
| 烟感 / 水浸 / 门禁 | 报警状态 | 1（报警） | 1（报警） |
| UPS | 电池容量（**低于**） | 40% | 20% |
| UPS | 负载率 / 机内温度 | 80% / 40°C | 90% / 50°C |
| 设备离线 | 失联 | — | 立即严重告警 |

界面上点 **「一键生成默认规则」** 即可一次性创建上面这套，之后随便改。

> 动环设备（温湿度/烟感/水浸/UPS）走 Modbus TCP，平台主动去轮询，
> 设备侧不用装任何东西。接法见 **第八章**。

## 二、三步配好告警

### 第 1 步：建通知渠道（告警配置 → 通知渠道 → 新建渠道）

| 渠道类型 | 适用场景 | 需要填什么 |
|---|---|---|
| 钉钉机器人 | 运维群实时提醒 | Webhook 地址 + 加签密钥（可选） |
| 企业微信机器人 | 推送到成员**微信** | Webhook 地址 |
| **短信平台（院内）** | 值班人员手机短信 | 平台 HTTP 接口地址 + 参数模板 |
| **电话告警盒子** | 严重故障语音呼叫 | 设备 HTTP 呼叫接口 + 参数模板 |
| 自定义 Webhook | 其他系统对接 | 任意 HTTP 地址 |

建完一定点 **「测试」**，收到消息才算配对；不确定参数对不对，点 **「预览」** 看渲染后的真实请求内容。

### 第 2 步：建/改告警规则（告警配置 → 告警规则）

一条规则包含：

- **监控对象 + 指标**：如 服务器 + CPU使用率
- **两级阈值**：提示阈值 / 告警阈值（如 80 / 90）
- **连续次数**：连续 N 次超限才告警，过滤瞬时抖动（默认 1 次）
- **静默期**：同一告警在 N 分钟内不重复打扰（默认 30 分钟）
- **通知级别**：只勾选「提示」或「严重告警」→ 该级别才推送
- **通知渠道**：可多选（不选则只入库不推送）
- **恢复通知**：指标回落时自动关闭告警并推送恢复消息

> **重要**：级别升级（提示 → 严重）会**立即再发一次**，不受静默期限制。
> 否则 82% 刚提示过、一路涨到 95% 反而不通知，是最容易出事故的情况。

典型用法：提示只发钉钉群；严重告警同时发钉钉 + 短信 + 电话呼叫。

### 第 3 步：验证

- 渠道页 **「测试」**：立刻收到一条测试消息
- 渠道页下方 **发送记录**：每次发送的成功/失败、平台返回内容都在这里，
  排查「为什么没收到告警」就看它

## 三、对接院内短信平台（重点）

医院内网的短信平台一般是 HTTP 接口，这里用 **通用 HTTP 网关** 对接，不绑定任何厂商。

**配置示例（表单格式）**

- 渠道类型：`短信平台 (院内)`
- 请求方式：`POST`
- 接口地址：`http://10.x.x.x:8080/sms/send`（换成平台真实地址）
- 请求头：`{"Content-Type":"application/x-www-form-urlencoded"}`
- 请求体模板：
  ```
  phone=13800138000&content={short}
  ```
- 成功标识：`code:0`（平台返回内容里包含这个字符串才算发送成功；留空则只看 HTTP 状态码）

**配置示例（JSON 格式）**

- 请求头：`{"Content-Type":"application/json"}`
- 请求体模板：
  ```json
  {"mobile":"13800138000","msg":"{short}","level":"{level}"}
  ```

**可用变量**（填在模板里，发送时自动替换）

| 变量 | 含义 | 示例 |
|---|---|---|
| `{short}` | 一句话摘要（**短信/电话首选**） | `web-prod-01 CPU使用率 95.0%超限` |
| `{title}` | 标题 | `【严重告警】 web-prod-01 CPU使用率` |
| `{content}` | 完整正文（Markdown，多行） | ... |
| `{level}` | 级别 | `critical` / `warning` / `info` |
| `{source}` | 告警对象 | `web-prod-01` |
| `{metric}` | 指标名 | `CPU使用率` |
| `{value}` | 当前值 | `95.0%` |
| `{time}` | 时间 | `2026-09-21 10:30:00` |

**号码与内容的别名**（各厂商参数名不一样，认哪个用哪个，号码只填一次）

| 类别 | 可用别名 |
|---|---|
| 号码（= 渠道里填的「被叫号码/接收号码」） | `{targets}` `{phone}` `{mobile}` `{tel}` `{called}` `{callee}` `{to}` `{number}` |
| 内容（电话盒子取**短句**；短信/Webhook 取完整正文） | `{tts}` `{text}` `{msg}` `{play}` `{message}` `{speak}` |

> 号码不要写死在模板里 —— 填在渠道的「被叫号码」字段里，模板里用
> `{phone}` 之类的变量引用。以后换值班号码只改那一个字段，模板不用动。

> 如果平台要求 GET 请求（参数拼在 URL 上），请求方式选 `GET`，变量同样直接写在「接口地址」里，例如
> `http://10.x.x.x:8080/sms/send?mobile=13800138000&msg={short}`

**联调建议**：先用一台能收到短信的手机号，点「测试」确认能收到；
再看下方「发送记录」里平台返回的原文，按返回内容调整「成功标识」。

## 四、对接电话告警盒子（通用）

- 渠道类型：`电话告警盒子`
- 被叫号码：填在独立字段里（多个逗号分隔）
- 接口地址：盒子提供的呼叫接口
- 请求体模板（按设备文档填），例如：
  ```
  called={called}&tts={tts}
  ```
  或 JSON：
  ```json
  {"callee":"{callee}","tts":"{tts}"}
  ```

**两点经验**
1. 语音播报用 `{tts}`（= 一句话摘要），**别用 `{content}`** ——
   完整正文念起来太长，值班的人听不下去。
2. **只在严重故障时打电话**：在规则里「通知级别」只勾「严重告警」、渠道只选电话盒子。
   80% 提示不打电话，90% 以上才呼叫，避免半夜被无关电话吵醒。

> 具体型号的实操见下一节（融智云 MFM-920E，就是你这台）。

## 五、对接融智云 MFM-920E 电话告警盒子（你这台）

你截图里那台是**融智云物联 MFM-920 系列「智能告警服务系统」**（产品型号 MFM-920E，
系统版本 3.7.6）。厂商官网 rzyiot.com 明确说明：提供 **HTTP API / TCP Client API /
RS-485 Modbus-RTU / RS-485 JSON** 四套接口，但**接口文档不公开**，随设备附送或找厂商要。

### 5.1 先把设备侧准备好

| 步骤 | 位置 | 说明 |
|---|---|---|
| 1. 插 SIM 卡 | 设备卡槽（抽屉式大卡） | 电话播报靠 4G 拨号，没卡打不出去 |
| 2. 确认信号 | 软件对应页面 | 搜索到运营商才算通 |
| 3. **记下设备 IP** | 软件左侧 **「本地网络」** | 这就是接口地址里的 IP |
| 4. 确认端口 | 软件 **「端口设置」** | HTTP 服务端口 `80`（默认）、TCP API 端口 `8000` |
| 5. 固定 IP | 路由器/交换机 | 建议给盒子配静态 IP，否则重启后 IP 变了告警就发不出去 |
| 6. 放通防火墙 | 平台服务器 | 允许平台服务器访问 `盒子IP:80`（否则连接被拒） |
| 7. 测试号码 | 软件内测试功能 | 先确认这台盒子自己能打通电话再对接平台 |

### 5.2 用探测器把接口路径扒出来

厂商不给文档不要紧 —— 这类盒子的 WEB 管理页面本身就是调 HTTP 接口驱动的，
把它的首页和 JS 抓下来就能看到真实接口路径。我在 `tools/probe_voice_box.py`
写了个探测器，**在能访问盒子的机器上**（比如你的运维电脑或平台服务器）执行。

脚本**零第三方依赖**（只用标准库 urllib），任意 python3 都能跑，不用装 httpx：

```bash
cd /opt/aiops-deploy/tools        # 部署包里已带
python3 probe_voice_box.py --ip 172.16.0.214

# 若 HTTP 端口不是 80
python3 probe_voice_box.py --ip 172.16.0.214 --port 8080
```

> 万一某台机器上确实不方便，也可以用后端虚拟环境里的解释器：
> `/opt/aiops-deploy/backend/venv/bin/python probe_voice_box.py --ip 172.16.0.214`
> （后端本身依赖 httpx，那个环境里一定有。）

它会做四件事：
1. 抓设备 WEB 页面，提取表单 action 与页面里的接口路径；
2. 下载页面引用的 JS，从中正则提取真实接口路径（**这一步最有效**）；
3. 逐个探测常见候选路径，自动过滤"兜底路由"（返回内容与首页相同的会标出来忽略）；
4. 给出结论和下一步命令。

> 探测模式全部用 GET 且**不带电话号码**，不会误触发拨号，可以放心跑。

拿到疑似路径后，用真实号码打一次验证（**会真的打电话**，确认号码再执行）：

```bash
python3 probe_voice_box.py --ip 172.16.0.214 --call \
    --path /api/xxx --phone 13800138000
```

### 5.2b 基础模式没探到时：换深度模式

基础扫描只试 80 端口、不登录。若返回"没探到明显接口"，用深度模式：

```bash
# 自动扫 80/8080/8000/8001/8888/5000/502/443(含 HTTPS)、自动尝试常见默认账号登录、
# 跟随页面链接找接口、对"HTTP 不通但端口开着"的端口做原始 TCP 探测
python3 probe_voice_box.py --ip 172.16.0.214 --deep

# 知道 WEB 登录账号密码时(接口通常要登录后才可见)
python3 probe_voice_box.py --ip 172.16.0.214 --deep --user admin --pass 123456

# 只想看某个 TCP 端口到底吐什么字节(比如 TCP Client API 的 8000)
python3 probe_voice_box.py --ip 172.16.0.214 --tcp 8000
python3 probe_voice_box.py --ip 172.16.0.214 --tcp 8000 --send "AT\r\n"
```

深度模式会输出：**每个端口返回什么**（确认 IP/端口对不对、要不要登录）、
**页面表单字段名**（拿不到账号时把它告诉对接人）、
**推断出的 WEB 根目录 + 该目录下所有管理页面里的接口路径**、
**页面内联 `<script>` 里写死的接口**（登录接口常藏在这）、
**TCP 端口的原始字节**（判断是不是 Modbus 之类的二进制协议）。

### 5.2b-2 页面要登录时：把浏览器 Cookie 复制给探测器 ★最有效★

你这台盒子的 WEB 页面带 `<title>登录</title>`，自动登录猜不出账号密码时，
**不用非得知道密码**——自己用浏览器登录成功后，把会话 Cookie 交给脚本，
脚本就能以"已登录"身份扫描所有管理页面，把接口路径扒出来。

**第 1 步：浏览器里登录盒子**

用能打开盒子 WEB 页面的电脑（你截图里那台），地址栏输入 `http://172.16.0.214`，
输入账号密码登录到管理首页。

**第 2 步：复制 Cookie**

1. 按 `F12` 打开开发者工具 → 切到 **Network**（网络）标签；
2. 按 `Ctrl+R` 刷新页面，请求列表里点**第一条**（一般就是 `172.16.0.214` 或 `login.html`）；
3. 右侧切到 **Headers**，往下找到 **Request Headers** 区；
4. 找到 `Cookie:` 这一行，**整行冒号后面的内容全部复制**。
   形如：`PHPSESSID=8f3a1c9d2e; username=admin; token=abc123`
   （如果这行很长，双击选中就能全选；有的浏览器是 `Cookie` 小写 `cookie`，都一样）

> 找不到 Cookie 这一行？切到 **Application** → 左侧 **Cookies** →
> 点域名，右边表格里的 `Name` / `Value` 自己拼成 `名=值; 名=值` 即可。

**第 3 步：带 Cookie 重跑探测器**

```bash
# 注意 Cookie 里有分号和空格, 必须用英文双引号包起来
python3 probe_voice_box.py --ip 172.16.0.214 --deep --cookie "PHPSESSID=8f3a1c9d2e; username=admin"

# 若设备还校验别的请求头(如 X-Token / Authorization), 一起带上
python3 probe_voice_box.py --ip 172.16.0.214 --deep \
    --cookie "PHPSESSID=8f3a1c9d2e" --header "X-Token: abc123"
```

看到 `已通过 --cookie 带入会话, 视为已登录` 就说明生效了。

**第 4 步：看输出里的关键信息**

```
[3] 抓页面 + 内联脚本 + 引用的 JS
    推断 WEB 根目录: /2/HTML/          ← 脚本从 JS 路径反推出的根目录
    JS http://172.16.0.214/2/HTML/js/alarm.js
      → /2/alarm/call                  ← 真实接口

[4] 扫 WEB 根目录下的管理页面
    http://172.16.0.214/2/HTML/alarm.html (路径 2 个)
      → /2/alarm/call
      → /2/alarm/list

[5] 逐个探测候选接口
    ✓ /2/alarm/call     200    ...     ← 状态码 200 且不是首页内容的就是真接口
```

把 **[4] 汇总发现的接口路径** 和 **[5] 里状态码 200 的路径** 贴给对接人，
就能确定接口地址；再对照 `alarm.html` 里的 `$.post("/2/alarm/call", {called:xx, tts:xx})`
这行代码，参数名也一并拿到（这里是 `called` 和 `tts`）。

> Cookie 有有效期，盒子重启或会话过期后要重新复制一次。

### 5.2b-3 已实测到的情报（融智云 MFM-920E，直接照抄）

从设备 Network 面板抓到的一条真实请求：

```bash
curl --url 'http://172.16.0.214/cgi-bin/about?_=1789960629606' \
  -b 'auth=YWRtaW46YWRtaW4%3D; roles=Super_Admin' \
  -H 'X-Requested-With: XMLHttpRequest' --insecure
```

由此确认三件事：

| 项目 | 结论 |
|---|---|
| **接口根目录** | `/cgi-bin/`，不是 `/api/`。页面文件在 `/2/HTML/`，接口在 `/cgi-bin/` |
| **WEB 账号密码** | **admin / admin** |
| **会话 Cookie** | `auth=YWRtaW46YWRtaW4%3D; roles=Super_Admin` |

**`auth` 的值是可以自己算出来的** —— 它就是 `base64(账号:密码)` 再做 URL 编码：

```
base64("admin:admin")            = YWRtaW46YWRtaW4=
URL 编码（= 变 %3D）             = YWRtaW46YWRtaW4%3D
```

**这意味着平台不需要走登录流程**，直接在请求头里带这个 Cookie 就能调接口。
所以平台上「请求头」这一栏填：

```json
{
  "Cookie": "auth=YWRtaW46YWRtaW4%3D; roles=Super_Admin",
  "X-Requested-With": "XMLHttpRequest",
  "Content-Type": "application/x-www-form-urlencoded"
}
```

> 改了设备 WEB 密码后，重算一次：`echo -n '账号:密码' | base64`，再把 `=` 换成 `%3D`。

**列出这台设备上到底有哪些 `/cgi-bin/` 接口**（在服务器上直接跑，不需要脚本）：

```bash
C='auth=YWRtaW46YWRtaW4%3D; roles=Super_Admin'
# ① 从页面和 JS 里把所有 /cgi-bin/ 引用捞出来（最准）
curl -s -b "$C" http://172.16.0.214/ -o /tmp/home.html
grep -oE '/cgi-bin/[A-Za-z0-9_.-]+' /tmp/home.html | sort -u
for j in $(grep -oE 'src="[^"]+\.js[^"]*"' /tmp/home.html | sed 's/.*src="//;s/"//'); do
  case "$j" in /*) u="http://172.16.0.214$j";; http*) u="$j";; *) u="http://172.16.0.214/$j";; esac
  curl -s -b "$C" "$u" | grep -oE '/cgi-bin/[A-Za-z0-9_.-]+'
done | sort -u

# ② 按常见名字暴力枚举一遍（① 没结果时用）
for n in about oem.cfg control.php msg_log.php system.php system_set.php \
         system_status.php call.php phone.php tel.php dial.php voice.php tts.php \
         alarm.php sms.php message.php send.php notify.php play.php record.php \
         log.php contact.php group.php user.php config.php setting.php \
         network.php status.php info.php version.php phone_book.php; do
  code=$(curl -s -o /tmp/r.txt -w '%{http_code}' -m 5 -b "$C" \
         -H 'X-Requested-With: XMLHttpRequest' "http://172.16.0.214/cgi-bin/$n")
  [ "$code" = "200" ] && echo "[$code] $n -> $(head -c 120 /tmp/r.txt)"
done
```

把输出贴出来即可确定「打电话」用哪个接口。已知线索：`control.php`
（名字带 control 且页面里有 `$.post("/cgi-bin/control.php", {cmd:"call", called:..., tts:...})`）
是最可能的拨号接口。

### 5.2b-4 首轮实测结果（172.16.0.214 已跑通）

带 Cookie 深度扫描的真实输出要点：

| 项目 | 实测值 |
|---|---|
| WEB 服务器 | **EdgeOS v3.7.3** |
| 开放端口 | **只有 80**（8000 是 TCP Client API，连上不发东西；502/8080 等全关） |
| 设备型号 | **MFM-920E**（`/cgi-bin/about` 返回 `productModel`） |
| 已确认接口 | `/cgi-bin/about`、`/cgi-bin/restart` → `{"Reply":"OK"}`、`/cgi_bin/expire`、`/login` |
| 菜单配置 | `/2/HTML/control_panel/{control_panel,msg_log,system_setting}_menu.cfg` |
| Cookie 有效期 | `expire: 4294967295`（0xFFFFFFFF）→ **永不过期** |

**两个必须记住的坑：**

1. **这台设备"路径不存在"返回的是 500，不是 404**。按 404 判会误报一大堆假接口。

### 5.4 参数名对不上怎么办

设备只认自己的参数名。点「预览」核对格式没问题、但设备不动作，就是**参数名不对**。
常见叫法我已经做成别名，挨个试最快：

| 位置 | 试这几个 |
|---|---|
| 号码字段 | `called` → `callee` → `phone` → `mobile` → `tel` → `to` → `number` |
| 内容字段 | `tts` → `text` → `msg` → `play` → `message` → `speak` |

模板里的**值**直接换成别名变量即可，例如把 `called={called}` 改成 `callee={callee}`。
号码字段不用动（都在「被叫号码」里，变量只是引用它）。

有些固件只把 HTTP 当 WEB 管理页用，告警触发走 **TCP Client API（8000）** —— 那就必须

1. **用盒子自己的"预制告警 + 触发"**：MFM-920 支持在 WEB 页面预制 250 条告警通知

2. **改用短信通道**：盒子也支持短信告警，把短信平台走 HTTP 网关先接上，
   电话作为第二步。

## 七、常见问题

| 现象 | 排查 |
|---|---|
| 配好了收不到消息 | 渠道页点「测试」；看下方「发送记录」的失败原因 |
| 钉钉报 `sign not match` | 「加签密钥」填错，或安全设置不是「加签」 |

## 八、动环设备接入（Modbus TCP）：温湿度 / 烟感 / 水浸 / UPS

院内的温湿度、烟感、水浸、UPS 一般是 RS-485 总线的 Modbus 设备，通过**串口服务器**
（也叫 Modbus 网关）转成 TCP。平台直接作为 Modbus TCP 主站去轮询，不需要在设备侧装任何东西。

界面上对应左侧菜单 **「动环设备」**。

### 8.1 先搞清楚一件事：一台设备要靠三个坐标定位

```
串口服务器 IP  +  该设备所在的 TCP 端口  +  Modbus 从站地址
     ↑                    ↑                      ↑
  192.168.x.x     一个端口 = 一段 RS-485      同一段总线上靠这个区分
```

一台串口服务器通常有 4/8/16 个 TCP 端口，每个端口接一段 RS-485 总线，
一段总线上还能再挂几十个从站。**所以只填 IP 是不够的**——同一台网关的
5302 端口是水浸、5305 端口是 UPS，从站地址又各自可能是 1~247 中的任意一个。

> ⚠️ 平台**只发读指令**（功能码 01/02/03/04），不会发任何写指令，
> 不存在误动 UPS 开关、误复位烟感的可能。这点在代码层面就限定死了。

### 8.2 第一步：用探测器把「寄存器映射」读出来

原始监控平台上一般只告诉你 IP、端口、Modbus 地址，**不会告诉你哪个寄存器是温度**。
所以先拿探测器连上去扫一遍。

`probe_modbus.py` 零依赖（只用 Python 标准库），拷到能访问这些设备的机器上直接跑：

```bash
# 单台扫一遍
python3 probe_modbus.py --dev 192.168.204.71:5001 --count 32

# 一次扫多台:  IP:端口:从站地址
python3 probe_modbus.py --dev 172.16.0.238:5302:1 \
                             172.16.0.238:5305:1 \
                             192.168.204.71:5001:1 \
                             192.168.204.71:5002:9

# 不知道从站地址时, 自动扫 1~16 号从站
python3 probe_modbus.py --dev 192.168.204.71:5001 --scan-slave

# 只看保持寄存器, 别刷屏
python3 probe_modbus.py --dev 192.168.204.71:5001 --only 3 --count 16
```

输出长这样（本地模拟环境实测）：

```
设备 127.0.0.1:5001   从站地址 1
  [保持寄存器] 功能码 0x03
    地址   原始值    有符号    ×0.1    说明
    0      256      256      25.6    ×0.1 → 25.6 ℃（温湿度探头: 0x0000=温度）
    1      634      634      63.4    ×0.1 → 63.4 %（温湿度探头: 0x0001=湿度）
  ✓ 读到 3 个非零点位
```

**看什么**：

| 现象 | 含义 |
|---|---|
| 温度/湿度那两个值乘 0.1 后落在合理范围 | 就是它，地址 0x0000 / 0x0001 |
| 全是 0 | 点位在更后面的地址（把 `--count` 调大），或从站地址不对（用 `--scan-slave`） |
| 全是 65535 | 通讯正常但设备内部量程没配 / 探头断线 |
| 报 `异常码 02` | 从站地址对上了，但读的地址区间超出设备范围（把 `--count` 调小） |
| 报 `超时` | IP/端口不通，或从站地址不对，或那一段 RS-485 没接 |

### 8.3 第二步：在平台上录入设备

菜单 **动环设备 → 新建设备**，四样必填：

| 字段 | 填什么 | 例（温湿度） |
|---|---|---|
| 设备名称 | 一眼能认出来的名字，会直接进告警短信 | 机房A_温湿度_1 |
| 设备类型 | 温湿度 / 烟感 / 水浸 / UPS / 配电 / 门禁 / 其他 | 温湿度 |
| IP + 端口 | 串口服务器 IP 和该设备的 TCP 端口 | 192.168.204.71 : 5001 |
| 从站地址 | Modbus slave id | 1 |

> 名称里带上位置，告警短信就不用再解释「哪个温湿度」。电话/短信字数有限，
> 建议控制在一行内。

**选完设备类型，平台会自动预置一套常见点位**，省得从零建：

| 设备类型 | 自动预置的点位 |
|---|---|
| 温湿度 | 温度(地址 0, ×0.1, ℃)、湿度(地址 1, ×0.1, %) |
| 烟感 | 烟雾状态(离散输入 地址 0, 0=正常 1=报警) |
| 水浸 | 漏水状态(线圈 地址 0, 0=正常 1=报警) |
| UPS | 输入电压、电池容量(×0.01)、负载率、机内温度 |

预置的是**行业最常见的默认值**，跟实测对不上的地方按 8.2 的结果改一下就行。

**设备多的时候用批量接口**，别在界面上点一百次：

```bash
curl -X POST http://<平台地址>/api/env/devices/batch \
  -H 'Content-Type: application/json' \
  -d '[
    {"name":"机房A_温湿度_1","category":"temp_humidity","ip":"192.168.204.71","port":5001,"slave_id":1,"location":"机房A-1排"},
    {"name":"机房A_烟感_1",  "category":"smoke",        "ip":"192.168.204.71","port":5002,"slave_id":9,"location":"机房A-顶棚"},
    {"name":"机房A_水浸_1",  "category":"water",        "ip":"172.16.0.238",  "port":5302,"slave_id":1,"location":"机房A-空调下方"},
    {"name":"机房A_UPS_1",   "category":"ups",          "ip":"172.16.0.238",  "port":5305,"slave_id":1,"location":"机房A-配电柜"}
  ]'
```

同名+同 IP+同端口的会自动跳过，重复执行不会灌出两份。

### 8.4 第三步：核对点位（「试读」按钮）

展开设备行能看到点位列表。改完地址/系数，先点 **「试读」**——它只读不落库，
确认读出来的值是对的再保存。

点位字段说明：

| 字段 | 含义 | 例子 |
|---|---|---|
| 功能码 | 01 线圈 / 02 离散输入 / 03 保持寄存器 / 04 输入寄存器 | 温湿度一般是 03 |
| 地址 | 0 基地址（有些设备手册从 40001 起算，减 40001 得到 0 基） | 0 |
| 数据类型 | u16 / s16 / u32 / s32 / bit | 温度一般 s16（有零下） |
| 位号 | 数据类型=bit 时取第几位（0 起） | 烟感多路时用 |
| 系数 | 原始值 × 系数 = 工程值 | 0.1 |
| 偏移 | 工程值 = 原始值 × 系数 + 偏移 | 0 |
| 单位 | ℃ / % / V / A | ℃ |
| 告警值 | 开关量报警时的值（0=正常 1=报警） | 1 |
| 点位标识 | 决定告警规则怎么匹配，见 8.5 | temperature |

**开关量的两种建模方式**（现场两种都常见，按实际情况选）：

- 设备是「一个寄存器多个通道」→ 功能码 02 + 地址 = 通道号（如第 3 路就填 2）
- 设备是「一个寄存器里用位表示」→ 功能码 02 + 地址 0 + 数据类型 bit + 位号 = 第几位

### 8.5 点位标识 → 告警规则

点位标识（key）把设备的读数和告警规则对上号。**没填标识的点位只显示不告警**。

| 点位标识 | 含义 | 默认阈值（提示/严重） | 方向 |
|---|---|---|---|
| temperature | 温度 | 30 / 35 ℃ | 高于 |
| humidity | 湿度 | 75 / 85 % | 高于 |
| smoke | 烟雾报警 | 1 / 1 | 高于 |
| water | 漏水报警 | 1 / 1 | 高于 |
| door | 门禁状态 | 1 / 1 | 高于 |
| power | 市电状态 | 1 / 1 | 高于 |
| ups_battery | UPS 电池容量 | 40 / 20 % | **低于** |
| ups_runtime | UPS 剩余续航 | 15 / 5 分钟 | **低于** |
| ups_load | UPS 负载率 | 80 / 90 % | 高于 |
| ups_temp | UPS 机内温度 | 40 / 50 ℃ | 高于 |

> ⚠️ **电池容量这类「越低越糟」的指标，比较符必须选「小于」。**
> 平台已按上表内置了正确方向；但如果你在「告警规则」里自己建同名规则，
> 比较符填反了会把电量充足的 75% 报成严重告警。
> 文案也会跟着变：方向对了才显示「电池容量**低于**告警阈值 18.0%」，
> 而不是错误的「达到告警阈值 75.0%」。

数据库里对某个 (类别, 指标) **一条规则都没有**时，平台用上表的默认阈值兜底，
保证开箱即用；一旦你在界面上建了该组合的规则，就以你配的为准
（全部禁用 = 明确关掉，不再用默认值）。

告警类别在通知里会自动细分（不用你配）：

```
【严重告警】消防 机房A_烟感_1(192.168.204.71) 烟雾报警达到告警阈值 1.0
【严重告警】漏水 机房A_水浸_1(172.16.0.238) 漏水报警达到告警阈值 1.0
【严重告警】UPS供电 机房A_UPS_1(172.16.0.238) UPS电池容量低于告警阈值 18.0%
【严重告警】温湿度 机房A_温湿度_1(192.168.204.71) 温度达到告警阈值 36.2℃
```

正文（钉钉/企微 Markdown）会长这样：

```
### 【严重告警】UPS供电 机房A_UPS_1(172.16.0.238) UPS电池容量低于告警阈值 18.0%

> **告警类别**: UPS供电 / 供电
> **对象**: 机房A_UPS_1
> **IP地址**: 172.16.0.238
> **指标**: UPS电池容量
> **当前值**: 18.0%　**阈值**: 20.0%
> **告警级别**: 严重告警
> **连续命中**: 3 次
> **规则**: UPS电池电量过低
> **时间**: 2026-09-21 14:32:10
```

### 8.6 轮询与恢复

| 机制 | 说明 |
|---|---|
| 自动轮询 | 每台设备可单独设「轮询间隔」（秒），默认 60；后台定时任务每分钟把所有启用的设备扫一遍 |
| 立即刷新 | 界面上「立即刷新全部」按钮，或 `POST /api/env/poll-all` |
| 单台轮询 | 设备行的「立即轮询」按钮，或 `POST /api/env/devices/{id}/poll` |
| 设备在线状态 | 通讯成功→online，连续失败→offline 并在设备上记 `last_error` |
| 历史曲线 | 每个点位最近 24 小时的值都落在 `env_point_readings` 表，`GET /api/env/points/{id}/history?hours=24` |
| 自动恢复 | 值回到阈值以内，告警自动关单；若规则勾了「恢复通知」会推一条恢复消息 |

> 轮询间隔别设太小。RS-485 是**半双工共享总线**，同一段总线上挂的设备合计
> 读写要排队，间隔 10 秒以下容易互相干扰、偶发超时。动环数据变化本来就慢，
> 建议 30~60 秒。

### 8.7 常见问题（动环部分）

| 现象 | 排查 |
|---|---|
| 全部点位 `超时` | 平台服务器到串口服务器的网络/防火墙没放通；`telnet <IP> <端口>` 验证 |
| 个别点位 `超时`，其他正常 | 从站地址填错，或该段 RS-485 没接好 |
| 报 `异常码 02` | 读的地址区间超出设备范围，把「点位数量/起始地址」调小 |
| 报 `异常码 03` | 设备拒收该数量，一次别读太多（探测器默认分批 16 个就是为这个） |
| 读回来全是 0 | 地址不对（往后试），或设备需要先写"启用位"（联系厂家要协议） |
| 温度值是 6553.5 这种离谱数 | 数据类型选错了：有零下的场景把 u16 换成 s16 |
| 温度 256 而不是 25.6 | 系数没填，填 0.1 |
| 同一个网关下有的通有的不通 | 串口服务器的端口和 RS-485 段对应关系记错了，拿探测器逐端口扫一遍 |
| UPS 显示离线但市电正常 | UPS 的通讯卡休眠了，看厂家手册有没有「通讯常开」设置 |
