# AIOps 运维平台 —— "长时间无操作后页面数据全部消失" 问题修复报告

> 修复日期：2026-09-21
> 影响范围：后端采集层 / 调度器 / 数据库访问 / 部署配置 / 前端请求层

---

## 一、问题现象

平台运行一段时间后（尤其是**闲置一段时间再回来**），出现：

| 现象 | 说明 |
|---|---|
| 页面框架正常显示 | 左侧菜单、顶部栏都能点，说明前端静态资源和 Nginx 正常 |
| 所有列表变空 | "服务器管理"显示"暂无数据" |
| 顶部弹出错误 | "服务器响应超时，请稍后重试" |
| **只能重启服务才能恢复** | `systemctl restart aiops-backend` 后立刻正常 |

关键点：**页面能打开但接口全挂**，而且**必须重启服务** —— 这说明不是网络问题，也不是浏览器问题，而是**后端进程虽然还活着，但已经无法正常响应请求了**。

---

## 二、根因定位（实测证据）

### 2.1 复现实验

编写了复现脚本 `tools/repro_leak.py`，模拟调度器每轮对交换机做 SNMP 采集，对比两种写法：

```
目标 127.0.0.1:161, 轮次 30

[A] 现状写法     句柄   359 ->   396  (增长   37)   asyncio任务    1 ->   31  (增长  30)
[B] 修复写法     句柄   396 ->   397  (增长    1)   asyncio任务   31 ->   32  (增长   1)
```

**结论：旧代码每次 SNMP 操作泄漏 1 个 socket 句柄 + 1 个永不退出的 asyncio 任务。**

### 2.2 泄漏是怎么发生的

旧代码 `snmp_service.py` 中：

```python
# 每次调用都新建一个 SnmpEngine —— 这是 pysnmp 明确反对的用法
async for (…) in walk_cmd(SnmpEngine(), …):
    if …:
        return          # 提前 return，异步生成器没有被关闭
    break               # 提前 break，同样没有关闭
```

两个问题叠加：

1. **每次新建 `SnmpEngine`**：它是重量级对象，内部持有 transportDispatcher 和事件循环任务，官方要求复用。
2. **`walk_cmd` 异步生成器提前 return/break 时不关闭**：底层 UDP socket 不会被释放。

### 2.3 放大效应

| 环节 | 数值 |
|---|---|
| 单台交换机一轮采集的 SNMP 操作次数 | 约 8 ~ 10 次（sysName、sysDescr、CPU 多个 OID、内存多个 OID、4 次端口表 walk） |
| 10 台交换机 | 每轮约 90 次操作 |
| 轮询频率 | 每 2 分钟一轮 |
| **每小时泄漏** | **约 2700 个文件描述符 + 2700 个悬空 asyncio 任务** |
| Linux 默认 `ulimit -n` | **1024** |

→ **几十分钟内文件描述符就耗尽。**

### 2.4 为什么表现成"必须重启"

1. **fd 耗尽** → SQLite 无法打开数据库文件、无法建立新连接 → 所有接口报错或超时；
2. **数千个悬空 asyncio 任务** → 事件循环调度开销剧增，CPU 被拉满，请求响应越来越慢；
3. 进程本身没崩溃，systemd 的 `Restart=always` 不会触发 → **只能人工重启**；
4. 重启后所有句柄和任务清零，服务立刻恢复正常 —— 与现场现象完全吻合。

### 2.5 帮凶（一并修复）

| # | 问题 | 后果 |
|---|---|---|
| 1 | 部署配置为 `--workers 2`，两个进程各跑一份 APScheduler | SNMP/VMware 轮询**双倍执行**，泄漏速度翻倍；两个进程争抢 SQLite 写锁 |
| 2 | Nginx `keepalive_timeout 60s` > 后端 `--timeout-keep-alive 30s` | 后端先关闭空闲连接，Nginx 仍复用这条死连接 → **闲置后第一次访问必然 502/超时** |
| 3 | 定时任务无 `max_instances` / `coalesce` / 总超时 | 设备不可达时单轮可跑几十分钟，任务持续堆积 |
| 4 | 历史曲线查询"全量查出来再内存切片" | 查 90 天数据时单台服务器十几万行（含 JSON），瞬间几百 MB 内存，可能被 OOM Killer 杀掉 |
| 5 | `server_metrics` 缺少复合索引 | 数据量到百万级后查询全表扫描 |
| 6 | 清理任务一次性 `DELETE` 大量历史数据 | 长时间占住 SQLite 写锁，期间所有接口等锁超时 |

## 三、修复内容

### 3.1 采集层 `app/services/snmp_service.py`（核心）

| 修复项 | 说明 |
|---|---|
| **全局复用单个 SnmpEngine** | 懒加载 + 锁保护，跟随事件循环绑定；提供 `close_engine()` 优雅释放 |
| **`aclosing` 包装所有 walk 生成器** | 无论是正常结束、提前 return、还是超时取消，生成器都会被正确关闭 |
| **单次操作硬超时** | GET/GETNEXT 6 秒、walk 25 秒，超时即取消，不再无限等待 |
| **并发限流** | 同时最多 6 个 SNMP 操作，避免瞬间打开大量句柄 |
| **设备级总超时** | 单台设备采集最长 75 秒，保证一轮轮询可控 |
| **Transport 缓存** | 相同 IP 复用 transport 对象 |

### 3.2 调度器 `app/services/scheduler.py`

- `max_instances=1` + `coalesce=True` + `misfire_grace_time=30`：**不再堆积**
- 每个任务再加一把重入锁和 `asyncio.wait_for` 总超时
- 每轮记录耗时/失败/超时次数，通过 `/api/health` 可查
- 新增 **`self_check` 自检任务**（每 2 分钟）：采集 fd / 内存 / asyncio 任务数，逼近上限时提前报错
- 清理任务改为**分批删除**（每批 5000 行，批次间让出事件循环）
- 设备之间 `await asyncio.sleep(0)`，保证 HTTP 请求不被饿死

### 3.3 数据库 `app/core/database.py`

- 连接池显式配置：`pool_size=5` / `max_overflow=10` / `pool_timeout=15` / `pool_recycle=1800` / `pool_pre_ping=True`
- `pool_timeout` 让池满时**快速失败**而不是无限挂起
- `get_db` 增加异常回滚，避免"带未结束事务的连接"回到池里堵住后续请求
- 新增复合索引：`server_metrics(server_id, collected_at)`、`env_readings(sensor_id, collected_at)`、`alerts(status, created_at)`
- 新增 `ping_db()` 供健康检查

### 3.4 查询接口 `app/api/servers.py`

- 历史曲线查询改为**先计数、再在 SQL 层用窗口函数均匀降采样**，硬上限 4000 行
- 数据库不支持窗口函数时自动回退到"硬限制 + 内存降采样"
- 新增日志记录降采样情况

### 3.5 应用入口 `app/main.py`

- `/api/health` 升级为**深度健康检查**：返回进程内存、fd 数、fd 上限、asyncio 任务数、数据库连通性与延迟、每个定时任务的执行状态
- 状态异常（数据库故障 / fd 超 90%）时返回 **HTTP 503**，让看门狗能感知"活着但已经亚健康"
- 新增 `/api/health/live` 极轻量存活探针
- 新增**多进程保护**：文件锁保证即使被配成 `--workers N`，定时任务也只在一个进程里跑
- 慢请求日志（> 5 秒）与未捕获异常兜底
- 优雅关闭：依次停调度器、关 SNMP engine、释放连接池
- `PEP` 修复：APScheduler 任务名改为可读的 job id

### 3.6 前端

- **新增连接监视器** `src/utils/connection.js`
  - 正常每 30 秒探活一次，异常时 5 秒重试一次
  - **页面从后台切回前台时立即探活**（正是"长时间无操作"的场景）
  - 后端恢复时广播 `aiops:backend-restored` 事件
- **请求层加固** `src/api/index.js`
  - 超时 30s → 20s
  - GET 重试 3 次、写操作 1 次，退避 0.5s → 1.5s → 3s
  - 主动取消 (`ERR_CANCELED`) 不重试
  - 长耗时接口（AI 对话、单台轮询、vCenter 同步）单独放宽超时
- **界面反馈** `components/Layout.vue`
  - 顶部显示连接状态横幅（含"已断开 xx 分钟"实时计时）
  - **后端恢复后自动重新挂载页面组件，自动拉取最新数据，无需手动刷新**

### 3.7 部署配置 `deploy/`

| 文件 | 关键改动 |
|---|---|
| `aiops-backend.service` | `--workers 1`（消除双份定时任务）、`--timeout-keep-alive 75`、`LimitNOFILE=65535`、`Restart=always` |
| `nginx-aiops.conf` | upstream `keepalive_timeout 55s`（**小于**后端 75s）、`proxy_next_upstream_timeout`、health 单独放行、长耗时接口单独放宽、index.html 不缓存 |
| `aiops-watchdog.sh` | 每 30 秒探活，**连续 3 次失败自动重启后端**，日志 5MB 自动轮转 |
| `aiops-watchdog.service` / `.timer` | systemd 定时触发看门狗 |
| `deploy-fix.sh` | 幂等一键部署：自动备份 → 更新代码 → 更新配置 → 重启 → 验证 |

### 4.1 单元级验证：SNMP 泄漏修复

`tools/repro_leak.py`：

| 写法 | 30 次调用句柄增长 | asyncio 任务增长 |
|---|---|---|
| 修复前 | **+37** | **+30** |
| 修复后 | **+1** | **+1** |

### 4.2 稳定性压力测试

`tools/stress_test.py` —— 模拟不可达交换机（**最坏情况**）连续采集 60 轮 × 5 次 SNMP 操作
共 **300 次操作**，耗时 740 秒：

```
    轮次       句柄    asyncio任务       内存MB   变化
------------------------------------------------------------
     0      362            1       44.7   基线
    10      340            2       45.2   句柄-22 任务+1 内存+0.5MB
    20      326            2       45.1   句柄-36 任务+1 内存+0.4MB
    30      325            2       45.2   句柄-37 任务+1 内存+0.5MB
    40      325            2       45.2   句柄-37 任务+1 内存+0.5MB
    50      325            2       45.1   句柄-37 任务+1 内存+0.4MB
    60      325            2       44.9   句柄-37 任务+1 内存+0.2MB
------------------------------------------------------------
耗时 739.7s, 共 60 轮 x 5 次SNMP操作 = 300 次操作
累计增长: 句柄 -37, asyncio任务 +1, 内存 +0.2MB
平均每次SNMP操作句柄增长: -0.1233 个
判定: 通过 —— 资源占用平稳, 无泄漏。
```

**从第 30 轮起曲线完全水平**：句柄恒定的 325、asyncio 任务 2 个、内存 45MB 不增不减。
（句柄从 362 降到 325 是启动时临时对象被 GC 回收所致，并非泄漏修复的功劳。）

对照修复前同脚本测得的数据：**每轮 +1.2 个句柄 +1 个 asyncio 任务，单调上升**。

## 五、部署方法

```bash
# 1. 上传并解压
tar -xzf aiops-fix-YYYYMMDD.tar.gz
cd aiops-fix-YYYYMMDD

# 2. 一键部署 (会自动备份 / 更新 / 重启 / 验证)
sudo bash deploy-fix.sh

# 3. 浏览器按 Ctrl+F5 强制刷新，加载新版前端
```

### 部署后建议观察项

```bash
# 后端健康检查（重点看 fds 是否随时间增长、scheduler 各项是否正常执行）
curl -s http://127.0.0.1:8080/api/health | python3 -m json.tool

# 自检日志（fd / 内存 / asyncio 任务数）
journalctl -u aiops-backend | grep 自检

# 定时任务耗时与超时
journalctl -u aiops-backend | grep scheduler

# 看门狗日志
tail -f /var/log/aiops-watchdog.log
```

## 六、回滚方法

每次部署都会自动备份到 `/opt/aiops-deploy/backup/`：

```bash
# 回滚后端代码
rm -rf /opt/aiops-deploy/backend/app
cp -r /opt/aiops-deploy/backup/app_<时间戳> /opt/aiops-deploy/backend/app
systemctl restart aiops-backend

# 回滚数据库
cp /opt/aiops-deploy/backup/aiops_<时间戳>.db /opt/aiops-deploy/backend/aiops.db
```

## 七、设计原则总结

本次修复遵循一条原则：**不依赖"记得手动重启"，而是让系统自己保持健康。**

| 层次 | 手段 |
|---|---|
| 不产生问题 | 修复 SNMP 泄漏（根因） |
| 不让问题放大 | 调度器防堆积 + 数据库连接池 + 查询降采样 |
| 提前发现 | 自检任务 + 深度健康检查 + 慢请求日志 |
| 自动恢复 | 看门狗 30 秒探活自动重启 + 前端自动重连刷新 |

即使将来出现本次未能预见的新问题，看门狗也会在 90 秒内自动重启服务，**用户不再需要手动操作**。
